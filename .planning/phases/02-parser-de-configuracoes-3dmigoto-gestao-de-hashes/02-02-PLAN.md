# Plan 02-02: Engine de cálculo e cache de hashes de recursos gráficos em tempo real

**Phase:** Phase 2: Parser de Configurações 3dmigoto & Gestão de Hashes
**Requirement(s):** CFG-02
**Goal:** Implementar o engine de hashing de recursos gráficos (Vertex Buffers, Index Buffers e Texturas) com cache por handle Vulkan, garantindo lookup O(1) durante o render sem introduzir stutter perceptível.

## Context

Para que a troca de recursos (Fase 3 e 4) funcione corretamente, o sistema precisa identificar cada `VkBuffer` e `VkImage` pelo mesmo hash de 32 bits (8 hex dígitos) que os mods do 3dmigoto usam. O hashing deve ser:
- **Rápido**: limitado aos primeiros N bytes do buffer para não bloquear o render thread.
- **Thread-safe**: draw calls chegam concorrentemente em engines multi-threaded.
- **Consistente**: o hash de um mesmo buffer deve ser estável entre frames enquanto o conteúdo não muda.

Algoritmo: **xxHash64** (header-only, zero dependências, ~10 GB/s em ARM64). Resultado truncado para `uint32_t` para compatibilidade com o formato 3dmigoto.

## Tasks

### Task 1: Integrar xxHash como third-party header-only
- **Goal:** Disponibilizar `xxhash.h` no projeto.
- **Files to create/modify:**
  - `third_party/xxhash/xxhash.h` *(single-header do repositório Cyan4973/xxHash)*
  - `third_party/xxhash/xxhash.c` *(arquivo de implementação opcional — pode usar define XXHASH_IMPLEMENTATION)*
  - `CMakeLists.txt` *(adicionar include dir `third_party/xxhash`)*
- **Details:**
  - Copiar apenas `xxhash.h` (modo single-header com `#define XXH_IMPLEMENTATION` antes do include em um único `.cpp`).
  - Criar `src/utils/xxhash_impl.cpp` contendo apenas o define + include para isolar a compilação.

### Task 2: Definir `HashRegistry` — cache de hashes por handle Vulkan
- **Goal:** Estrutura de dados thread-safe que mapeia handles Vulkan (`VkBuffer` / `VkImage`) para seus hashes calculados.
- **Files to create/modify:**
  - `include/hash/hash_registry.h`
  - `src/hash/hash_registry.cpp`
- **Details:**
  - `struct HashEntry { uint64_t hash64; uint32_t hash32; /* truncado para formato 3dmigoto */ }`
  - `class HashRegistry`:
    - `std::shared_mutex m_mtx` para read-heavy concurrency
    - `std::unordered_map<VkBuffer, HashEntry> m_buffer_hashes`
    - `std::unordered_map<VkImage, HashEntry> m_image_hashes`
  - API pública:
    - `std::optional<HashEntry> get_buffer(VkBuffer buf) const noexcept`
    - `std::optional<HashEntry> get_image(VkImage img) const noexcept`
    - `void store_buffer(VkBuffer buf, HashEntry entry) noexcept`
    - `void store_image(VkImage img, HashEntry entry) noexcept`
    - `void evict_buffer(VkBuffer buf) noexcept` ← chamado em `vkDestroyBuffer`
    - `void evict_image(VkImage img) noexcept` ← chamado em `vkDestroyImage`
  - `HashRegistry::instance()` — singleton de acesso global.

### Task 3: Implementar `ResourceHashEngine` — computação do hash em tempo de render
- **Goal:** Motor que calcula o hash xxHash64 de um buffer/imagem Vulkan a partir de sua memória mapeada, com cache automático.
- **Files to create/modify:**
  - `include/hash/resource_hash_engine.h`
  - `src/hash/resource_hash_engine.cpp`
- **Details:**
  - `class ResourceHashEngine`:
    - `uint32_t hash_buffer(VkDevice device, VkBuffer buffer, VkDeviceMemory memory, VkDeviceSize offset, VkDeviceSize size) noexcept`
      - Verifica `HashRegistry` primeiro (cache hit → retorna imediatamente).
      - Em cache miss: `vkMapMemory` nos primeiros `min(size, GIMI_HASH_SAMPLE_BYTES)` bytes.
      - Calcula `XXH64(data, sample_size, 0)`, armazena no `HashRegistry`, retorna `hash & 0xFFFFFFFF` (truncado para 32 bits).
      - `vkUnmapMemory` imediatamente após o hash (não manter mapeamento).
    - `uint32_t hash_image(VkDevice device, VkImage image, VkImageCreateInfo info) noexcept`
      - Para imagens, usa fingerprint de metadados (width, height, format, mipLevels) como hash para evitar custo de mapear VRAM.
      - `XXH64(&info_subset, sizeof(info_subset), 0)` onde `info_subset = {width, height, format, mipLevels, arrayLayers}`.
  - Constante de compilação: `GIMI_HASH_SAMPLE_BYTES = 4096` (ajustável via CMake `-DGIMI_HASH_SAMPLE_BYTES=<N>`).

### Task 4: Conectar eviction hooks ao Vulkan Layer (Phase 1)
- **Goal:** Garantir que hashes de buffers/imagens destruídos sejam removidos do cache para evitar stale entries.
- **Files to create/modify:**
  - `src/graphics/vulkan_layer.cpp` *(adicionar interceptors de `vkDestroyBuffer` e `vkDestroyImage`)*
  - `include/graphics/vulkan_layer.h` *(adicionar entradas nas DeviceDispatchTable)*
- **Details:**
  - Interceptar `vkDestroyBuffer(device, buffer, pAllocator)`:
    - Chamar `HashRegistry::instance().evict_buffer(buffer)` antes de forwarding.
  - Interceptar `vkDestroyImage(device, image, pAllocator)`:
    - Chamar `HashRegistry::instance().evict_image(image)` antes de forwarding.
  - Adicionar `PFN_vkDestroyBuffer DestroyBuffer` e `PFN_vkDestroyImage DestroyImage` à `DeviceDispatchTable`.

---

## Verification Criteria

1. `ResourceHashEngine::hash_buffer()` retorna o mesmo hash (`uint32_t`) para o mesmo conteúdo de buffer em chamadas consecutivas (estabilidade de cache).
2. Após `vkDestroyBuffer`, `HashRegistry::get_buffer()` retorna `std::nullopt` (eviction funcionando).
3. O tempo de `hash_buffer()` em cache miss com buffer de 1 MB é < 500 µs (amostragem limitada a `GIMI_HASH_SAMPLE_BYTES`).
4. `hash_image()` usando metadados é determinístico para a mesma `VkImageCreateInfo`.
5. Acesso concorrente ao `HashRegistry` a partir de múltiplas threads não gera race conditions (verificado com ThreadSanitizer em build de desenvolvimento).
