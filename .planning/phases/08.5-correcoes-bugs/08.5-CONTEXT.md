# Phase 8.5 Context: Correções de Bugs (Shizuku, Storage & Injeção)

## Phase Goal
Investigar a fundo e corrigir os problemas arquiteturais e de permissões do Android que estão bloqueando o funcionamento do GIMI Launcher: a lista de mods vazia, falha na injeção da Vulkan Layer e detecção inexistente do Shizuku.

## Análise dos Problemas (Root Causes)

1. **Lista de Mods Vazia (Storage Permissions)**
   - O aplicativo possui a permissão `MANAGE_EXTERNAL_STORAGE` no `AndroidManifest.xml`, mas no Android 11+ (Target SDK 34) esta permissão não é concedida automaticamente. O usuário deve ser redirecionado para a tela de configurações para permitir o "Acesso a Todos os Arquivos". Como o app não faz esse pedido em tempo de execução, a chamada C++ `std::filesystem` tem o acesso negado à pasta `/sdcard/GIMI/Mods`.

2. **Detecção do Shizuku Falha (`is_shizuku_available`)**
   - O código nativo tenta rodar `system("which shizuku")` e `system("settings ...")`. Aplicativos Android regulares não têm acesso à binários do shell de root/ADB diretamente pelo PATH, nem possuem permissão `WRITE_SECURE_SETTINGS`. Portanto, todos os comandos do `system()` falham silenciosamente (código de saída não-zero).
   - O Shizuku real deve ser detectado checando a disponibilidade do serviço Binder do Shizuku ou solicitando a permissão do Shizuku (`moe.shizuku.manager.permission.API_V23`).

3. **Injeção da Vulkan Layer Falha (`enable_layer`)**
   - A injeção tenta invocar `system("settings put global enable_gpu_debug_layers 1")`. Novamente, como o app não possui o privilégio `WRITE_SECURE_SETTINGS` e o Shizuku não está sendo usado nativamente através da API Java, o sistema bloqueia a alteração.

## Key Architectural Decisions
Para corrigir isso sem precisar compilar dependências complexas (AIDL/Shizuku SDK) no ambiente restrito do Termux, optaremos por:
1. **Permissões em Runtime:**
   - Adicionar código em `MainActivity.java` para verificar e solicitar ativamente `Environment.isExternalStorageManager()`. Se falso, abrir `Settings.ACTION_MANAGE_APP_ALL_FILES_ACCESS_PERMISSION`.
2. **Integração Shizuku via Java Reflection ou rish:**
   - Se o usuário tiver o Shizuku, o comando `rish` pode não estar no PATH. O método correto sem importar as bibliotecas completas do Shizuku é usar o shell `/data/local/tmp/shizuku/shizuku` ou focar na permissão ADB manual se o Shizuku não puder ser chamado via command-line.
   - Alternativa: Como estamos em um MVP e a integração completa do SDK do Shizuku via `d8`/`javac` puro é muito complexa, o Launcher vai utilizar um fallback ADB nativo ou solicitar que o usuário rode um script via ADB que conceda `WRITE_SECURE_SETTINGS` ao app. Após obter `WRITE_SECURE_SETTINGS`, o app pode usar `Settings.Global.putInt(...)` diretamente em Java sem precisar do shell!

## Requisitos
- [FIX-8.5-01] O App deve solicitar acesso a Todos os Arquivos na inicialização.
- [FIX-8.5-02] O App deve usar a API Java `Settings.Global` para injetar a layer (que é muito mais limpo do que `system("settings...")`).
- [FIX-8.5-03] O App deve orientar o usuário a conceder a permissão `WRITE_SECURE_SETTINGS` via Shizuku/ADB (exibindo um aviso/botão) se a permissão estiver ausente.
